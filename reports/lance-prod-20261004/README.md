# Lance 生产化验收（合成数据 1,000 万条），2026-10-04

**结论：在 1,000 万条合成数据上，导入、按 ID 查询、Layer 回写、版本治理、镜像和分片训练读取均已跑通，设定的门槛全部达标；外推到 9,278 万条也在可接受范围内。正式在 catalog 登记之前，还需用真实全量数据和真实 COS/OBS 各跑一次。** 使用说明见 [Lance 物化后端](../../docs/lance-materialization.md)，完整数据见 [results.json](results.json)。

## 环境与数据

- Python 3.12.3、pylance 12.0.0、PyArrow 25.0.1；128 核、1 TB 内存、本地盘。
- 1,000 万条合成 AudioRecord（JSONL.gz，147 MB）：单音频槽位，中英各半，10% 为 dev split，1/3 为 `clean.pass=false`。字段结构与真实数据一致，但文本和 metadata 更短，真实数据的表体积和解码耗时会更大。
- 脚本：`scripts/lance_scale_acceptance.py --workers 8 --shards 8 --layer-sizes 1 64 100000 1000000`。每项操作在独立进程中运行，RSS 为该进程自身峰值；冷读前清除表文件的页缓存。

## 发现与限制

1. **大结果查询的耗时主要是 Python 解码**：每条约 20 µs（JSON → AudioRecord），与 Lance 本身无关。按 ID 等选择性查询收益明显；需要导出几百万条时，应使用 `export` 或分片流式读取。
2. **分片大小不均**：8 个分片中，最多 206 万条，最少 94 万条。原因是按 fragment 分片，而压缩后 fragment 大小不一。全量约 350 个 fragment，差异会缩小，但分布式训练仍不能假设各 rank 的 batch 数相同。
3. **保留所有已发布版本会保留它们的数据**：经过 4 个 Layer 和一次压缩后，表从 4.7 GB 增至 8.4 GB，cleanup 只能删除未打 tag 的版本。要回收空间，需先确认某个已发布快照不再被任何 View 或 catalog 引用，再删除它的 tag（目前尚无封装命令）。
4. **合并内存**：Lance 合并时的哈希连接不能落盘，100 万条 patch 需约 3.9 GB。适配器已按暂存大小自动设置内存池；更大的批次建议拆成多个 Layer。
5. **对象存储**：本次镜像目标是本地 `file://` URL，与 `s3://` 走同一套 Lance / pyarrow 代码，但没有连接真实 COS/OBS。需在有凭据的机器上执行一次 `mirror` 并按固定版本读取。
6. **verify 较慢**：全量约 2.5 小时，适合放在转正验收或定期巡检中，不适合每次发布都跑。
